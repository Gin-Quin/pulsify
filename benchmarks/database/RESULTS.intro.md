# Database benchmark results

PostgreSQL, SQLite, RocksDB, LevelDB and LMDB storing and serving real Pulsify
histories on the same dedicated server, measured on 2026-11-11.
[Method, adapters and commands](README.md) ·
[raw reports](../baselines/database-f4-metal-small-20261111).

This file is generated by `benchmarks/database/dedicated/report.ts` from the
raw reports; its introduction is [`RESULTS.intro.md`](RESULTS.intro.md).

## Server

| | |
|---|---|
| Machine | Latitude.sh `f4.metal.small`, London, bare metal |
| Processor | AMD EPYC 4484PX, 12 cores, SMT off, `performance` governor |
| Memory | 96 GB |
| Storage | Samsung PM9A3 960 GB NVMe, dedicated to the database, ext4 `noatime` |
| System | Ubuntu 24.04.5, Linux 6.8.0-147 |
| Software | Rust 1.99.1, Clang 18, Bun 1.4.4 |

Two servers of this model, in the same site, shared the work so that it would
finish sooner: server A ran PostgreSQL and LMDB, server B ran SQLite, RocksDB
and LevelDB. One engine ran at a time, alone on its machine. Both servers first
ran the same control series (SQLite, 8 cores, 1,000 edits, both tiers, 36
cells): their throughputs differ by 1.5% in the median, by 9% at most for the
batches that lasted a quarter of a second or more, and by up to 25% for the
shorter ones. LevelDB's whole campaign also ran on server A
([`repeat-a`](../baselines/database-f4-metal-small-20261111/repeat-a)): against
the series published here, the median difference is 1.9%, nine cells in ten are
within 7%, and the shortest batch differs by 30%.

## What is measured

| Axis | Values |
|---|---|
| Cores | 1, 4, 8: the other cores are taken offline in the kernel |
| Document history | 100, 1,000, 10,000 edits on the same 256-paragraph, 266 KiB document |
| Durability | strict: a commit is flushed to disk before it is acknowledged. Relaxed: acknowledged first, flushed shortly after |
| Concurrent clients | 1, 16, 128, each sending its next request when the previous one returns |
| Scenario | the mixed workload, then each of its five operations alone |

That is 324 cells per engine. A cell is a batch of **2,000 requests on one
document**: throughput is the successful requests divided by the time the
batch took; latency is the time one request took from the client's side,
lock waits included.

- **The same work for every engine.** One Rust runner holds the storage policy
  (causal checks, version vectors, compaction plans, checksums) and calls each
  engine through the same five primitives. The request schedule, the documents
  and the patches are identical. After each cell the runner reads every
  document back and compares it row for row with what was accepted; a sample
  is then replayed through Pulsify itself.
- **Clients and database share the cores.** The embedded engines run inside
  the client process; PostgreSQL is a server on the same machine, reached
  through a Unix socket.
- **Reads include the client's work.** A read fetches the segments, verifies
  their checksums and decodes them. With a 10,000-edit history this costs more
  than the fetch itself, for every engine alike, so the engines draw closer
  together as the history grows.
- **Each cell starts from a settled store.** Its documents are seeded and
  persisted before the timer starts. When it ends, the engine finishes outside
  the timer what it deferred: checkpoint, flush, compaction.
- **Nothing is deleted.** Each engine keeps one database for its whole
  campaign, which grows to about 30 GiB of payload.

## Engines

Each engine runs with the configuration that suits this workload on this
machine. Those with a cache of their own get the same 16 GiB.

| Engine | Version | Strict | Relaxed | Configuration |
|---|---|---|---|---|
| PostgreSQL | 18.6 | `synchronous_commit=on` | `synchronous_commit=off` | `shared_buffers` 16 GiB, `max_wal_size` 32 GiB, 15-minute checkpoints, LZ4 for TOAST and WAL, `jit` off, `C` locale, data checksums (the default) |
| SQLite | 3.51.1 | WAL, `synchronous=FULL` | WAL, `synchronous=NORMAL` | memory-mapped reads, 64 MiB page cache per connection, checkpoint every 64 MiB of log |
| RocksDB | 11.8.1 | WAL synced on every commit | WAL written, not synced | `TransactionDB`, 16 GiB block cache, one background thread per core, LZ4 then ZSTD on the last level, Bloom filters, blob files for values of 4 KiB or more |
| LevelDB | 1.22 | log synced on every write | log written, not synced | 16 GiB block cache, 64 MiB write buffer, Snappy |
| LMDB | 0.9.70 | synced on every commit | `MDB_NOSYNC` | defaults: it reads through the page cache and has nothing else to tune |

LevelDB has no transactions and no lock manager: its adapter serializes one
document's writers with a mutex and commits one write batch per transaction.

## In short

- **LMDB is the fastest on the mixed workload** in 53 of the 54 configurations,
  and on reads in most of them.
- **LevelDB appends single patches fastest** (51 of 54), ahead of RocksDB and
  LMDB. PostgreSQL wins 12 of the 27 strict full-document write cells, LMDB all
  the others.
- **On the mixed workload with 16 or 128 clients, SQLite and PostgreSQL are
  behind the three key-value engines** in every configuration. SQLite leads no
  cell.
- **On disk**, the engines that compress (LevelDB, RocksDB, PostgreSQL) hold the
  campaign in 6 to 9 GiB; SQLite and LMDB, which do not, in 31 GiB.

## Reading these numbers

- **One run per cell.** From the two repeated series above, a difference under
  10% between two engines is not a ranking. A third of the cells (509 of 1,620,
  mostly compaction checks, patch appends and reads from a version vector)
  lasted less than a quarter of a second: there, read anything under a factor
  of 1.3 as noise.
- **One document.** Its writers are serialized by every engine, so extra cores
  help the readers and the clients' own work, not a single writer. With one
  client, going from 1 to 8 cores brings 0% to 13% on the mix for the embedded
  engines and 23% for PostgreSQL, whose server is a second process; with 128
  clients it brings 3 to 7 times more.
- **PostgreSQL's request errors.** 919 requests failed, all of them compaction
  attempts inside the mixed workload at 16 clients (19) and 128 clients (900):
  the attempt gave up after its plan went stale 32 times in a row. Nothing is
  lost, the history simply stays uncompacted. The cells concerned show their
  error count and are left out of the row's ranking. No other engine had an
  error.
- **Strict depends on the drive.** This one has power-loss protection and
  flushes a commit in about a tenth of a millisecond. A drive without it would
  widen the gap between the two tiers.
- **Size on disk is mostly compression.** The payload is repetitive English
  text. PostgreSQL (LZ4), RocksDB (LZ4, ZSTD) and LevelDB (Snappy) compress it;
  SQLite and LMDB store it as it is. Another corpus compresses differently.
- **Finite batches.** They compare engines under the same load; they are not
  capacity estimates. Each engine was measured for 10 to 22 minutes in total.
- **Not comparable with the earlier campaigns**, which ran other
  configurations, on other hosts, with batches of 1,000 requests.
